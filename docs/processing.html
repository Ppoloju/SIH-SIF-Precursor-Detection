Technical Documentation

How data is processed, and which algorithm decides every field

This page documents the actual pipeline that runs in this repository: where a file goes after upload, every processing stage it passes through, and the specific algorithm that determines the result of each output field — with the module names so the claims can be checked against the source.

01 · Processing Stages

The journey of a file, stage by stage

1
Upload or paste CSV / TSV / TXT / JSON / XLSX (XLSX needs the optional openpyxl package). A row is a report; jobs run inline or in the background with progress stored in the database. Module: ingest.py (parse_rows, start_import_job)
↓
2
Auto column mapping headers are normalized (lowercase, punctuation stripped) and scored against synonym lists for each canonical slot (text, title, date, site, activity, report_type, report_id, hazard, consequence, barrier_failure, location, equipment, unsafe_type, rule). Assignment is greedy by score so a generic "type" column never becomes the report text and Site_name beats Location_detail for the site slot. The mapping can be overridden per upload. Module: ingest.py (_auto_map_columns, resolve_mapping)
↓
3
Row normalization dates parsed across common formats, title joined before the report text, Site_name + Location_detail merged, cell values cleaned. Free text is what the AI analyzes; structured columns are kept as candidates for authoritative overrides. Module: ingest.py (normalize_row)
↓
4
Duplicate fingerprinting each row's text is fingerprinted (lowercased, whitespace/punctuation collapsed, Indic scripts preserved). A row whose text already exists in the database — or repeats inside the same file — is skipped and reported as "duplicate of ...", never stored twice. Module: ingest.py (_text_fingerprint, duplicate check)
↓
5
Analysis per report every unique row runs through the full engine: indicator detection, rule mapping, extraction, scoring, narrative — detailed in the field table below. Module: analysis_pipeline.py (analyze_report)
↓
6
File overrides applied when the file provides a structured value (hazard, activity, rule, consequence, barrier_failure, location, equipment, unsafe_type), that value is used as-is — it is the authority. The AI's own extraction is retained in the record for reference only; if the file overrides the Life-Saving Rule, the rule-condition map is cleared so the two never contradict. Module: ingest.py (_apply_file_overrides)
↓
7
Rule estimation fallback if neither the text nor a file column produced a Life-Saving Rule, the rule is estimated from the file's structured hazard/activity values (e.g. hazard "confined space entry" to Confined Space Entry) and the derivation is stated in the uncertainty note — the field is never left blank when derivable. Module: ingest.py (estimate_rule_from_fields)
↓
8
Persist report + analysis one Report row and one Analysis row per report, committed progressively (every 10 rows in job mode) so the UI shows live progress. The database schema is created/migrated additively on startup. Modules: models/db.py, models/entities.py
↓
9
HSE review closes the loop stored analyses land in the HSE review queue; human decisions (verify / not SIF / edits) are stored as labeled examples and drive the retraining pass. Modules: api/review.py, services/adaptive.py
02 · Field by Field

Which algorithm determines the result of each field

Every field of a stored analysis, and the exact method that produces it. The pipeline is hybrid: deterministic rule/NLP layers answer first, an optional LLM (Llama via Groq) may only polish wording, and file-provided structured values always win over text extraction.

Output fieldAlgorithm / decision ruleModule
sif_potentialTrue when at least one SIF indicator matches the text. Indicators come from a keyword/phrase lexicon organized per Life-Saving Rule, matched with negation detection ("without isolation", "no permit", "missing guard") so a control that is present is not flagged. English patterns run first, then Hindi / Bengali / Assamese (native script and romanised) patterns; overlapping same-rule matches are de-duplicated. Verdict: risk_scorer.assess returns False when no match survives.sif_detector.py, multilingual.py, risk_scorer.py
confidence0.55 when no indicators matched. Otherwise min(0.97, 0.62 + 0.11 * indicators + 0.05 * severity) where severity is the consequence bonus (2 for fatality/serious-injury wording, else 1).risk_scorer.py
priority (HIGH / MEDIUM / LOW)Additive prototype score of four stored factors — matched indicators (capped at 3), consequence severity (0–2), people exposure (0–1), barrier failure (0–1). HIGH at score ≥ 5, MEDIUM at ≥ 3, else LOW. The factors are persisted per report and shown as a "how it was calculated" breakdown. Explicitly not an official OIL risk methodology.risk_scorer.py
life_saving_ruleThe primary rule among the matched indicators (rule classifier picks the most relevant rule and reports its confidence). A file rule column overrides this; if nothing matched and no file value exists, the rule is estimated from hazard/activity fields. One of the canonical ten: Work Authorization, Energy Isolation, Bypassing Safety Controls, Confined Space Entry, Working at Height, Safe Mechanical Lifting, Toxic Gas Safety, Driving Safety, Line of Fire, Hot Work Safety.rule_classifier.py, ingest.py
hazardFirst hazard from the extractor's hazard list (lexicon-driven phrases in the text), or the file's hazard column when provided. Not fabricated: reports with no hazard wording get "Not stated".information_extractor.py, ingest.py
potential_consequenceThe consequence label of the strongest matched indicator (the lexicon assigns each indicator phrase a potential consequence such as fatality / serious injury / fire / exposure).safety_lexicon.py
barrier_failureBarriers that were negated or described as missing/defeated in the text (gas testing, isolation, permits, guards...), merged with a file barrier_failure column when present.information_extractor.py, ingest.py
activityExtracted activity phrase (maintenance, welding, entry...). When the report never states it, it is inferred from the mapped rule's typical activity table and flagged as inferred in the explanation; a file activity column is used as-is.information_extractor.py, safety_lexicon.py
locationLocation phrase extracted from text with its evidence; a file location column wins. Inferred-from-text locations are flagged in the explanation.information_extractor.py
equipmentDe-duplicated union of English equipment extraction and foreign-language equipment terms; a file equipment list is used when provided.information_extractor.py, multilingual.py
unsafe_typeUnsafe Act / Unsafe Condition / Near Miss classification from the text (or the file's own classification, used as-is).information_extractor.py, ingest.py
rule_conditionsEach condition of the mapped Life-Saving Rule is matched against the text and labeled breached / in_place / not_verifiable, each with the exact quoted wording it was inferred from. Cleared when a file rule override contradicts the AI's rule.rule_mapper.py
evidenceThe exact matched indicator phrases, quoted verbatim in the original language — the literal reason a verdict was raised.sif_detector.py, multilingual.py
languagesScript detection (Devanagari / Bengali / Assamese) plus romanised lexicon detection, reported as codes such as en, hi, hi-latn, bn, bn-latn, as, as-latn.multilingual.py
summaryDeterministic three-part plain-language narrative (what happened / why it matters / next step) built from the structured result, with breached conditions appended. An optional LLM pass may rephrase it into the report's language; on any failure the deterministic text stands.narrative.py, llm.py
suggested_actionsRule-based corrective-action checklist generated from the mapped rule profile and the failed barriers (verify gas testing, reinstate standby, re-isolate, brief the crew, escalate when HIGH).narrative.py
explanationDeterministic explanation grounded in the report: quotes the sentence around the first evidence, names the hazard, rule and affected barriers, lists breached conditions, and flags any inferred field. LLM refinement may polish phrasing only.analysis_pipeline.py (build_explanation), llm.py
uncertainty_noteHonest caveats only: a rule estimated from file fields, an inferred value, or a learned-signal flag. Never used to fabricate content.ingest.py, adaptive.py
model / llm_refinedProvenance tag of the run: rules-v1 deterministic, rules-v1+llm after LLM polish, rules-v1+tuned when learned review signals were applied.analysis_pipeline.py, adaptive.py
similarity score (with past reports)Hybrid: normalized token overlap of the texts plus shared-concept bonuses for the same rule / hazard / barrier / activity (bonuses capped low so genuine near-copies outscore distinct-but-related precursors). Reported with the shared fields so an HSE reviewer can see why two reports are linked.similarity.py
duplicate / duplicate_ofExact duplicates are prevented at import by the text fingerprint; stored near-copies at similarity ≥ 0.88 are flagged duplicate_of with a compare link (threshold constant DUP_SIMILARITY).ingest.py, api/reports.py
review statusHuman decision state per report — pending by default, then HSE verified / rejected / edited. Feedbacks are stored as labeled examples for retraining.api/review.py
aggregate fields (trend, density, patterns)Weekly buckets of analyzed reports; SIF precursor density = SIF-potential reports ÷ total reports; recurring patterns group ≥ 2 SIF-potential reports by rule+activity / rule+barrier / hazard+activity, always backed by the real member reports.api/analytics.py

Structured file values used "as-is" replace the text-extraction value in the stored record; the AI-extracted value is retained inside the record for reference and never silently merged.

03 · Scores Explained

Nothing is a black-box number

confidence = min(0.97, 0.62 + 0.11 * matched_indicators + 0.05 * severity_bonus) # 0.55 when nothing matched priority = add( matched_indicators (cap 3) , severity_bonus # 2 if consequence says fatality / serious injury, else 1 , exposure_bonus # 1 if people were exposed (actors/actions present) , barrier_bonus # 1 if a control was negated or missing ("without", "no", "missing", "bypass", "failed"...) ) HIGH when score >= 5 MEDIUM when score >= 3 LOW otherwise sif_density (weekly) = SIF-potential reports / total reports in that week

Why these four factors?

They mirror how an HSE reviewer triages a report: how many precursor signals are present, how bad the plausible outcome is, whether people were actually exposed, and whether a control was defeated. Each factor is stored per report and shown as its own row in the UI breakdown, so the total is auditable.

What it is not

The score is an AI-assisted prototype priority intended for early warning and queue ordering. It is not an official OIL risk matrix, and every HIGH/priority surface in the app says so and routes the decision to HSE review.

04 · Similarity, Duplicates, References

How reports are linked to history

  • Similarity means "same precursor, same context": the score combines how much of the text overlaps (token-level) with whether the two reports share the mapped rule, hazard, barrier or activity. Each shared concept adds a small bonus; the caps keep distinct-but-related precursors from outscoring genuine near-copies.
  • The reviewer can audit the link: the report page shows the similarity score together with the fields the two reports share, so the number is explainable rather than opaque.
  • Duplicates are explicit: import-time fingerprinting refuses to store a row whose text already exists (reported as skipped duplicates), and stored reports at similarity ≥ 0.88 are flagged as near-copies with a compare link.
  • Solved case as a reference (site A to site B): when a fresh report matches a past case that another site already reviewed and verified (ideally with action notes), the page highlights that case as the reference and asks HSE to check whether the same corrective action applies — pattern and reference pages open the real member reports, never inline examples.
05 · Evaluation & Retraining

Measured, then improved by HSE labels

Deterministic benchmark

A hand-labeled golden set of 35 reports (English, Hindi, Bengali, Assamese) is scored per class and per Life-Saving Rule with precision / recall / F1 plus a confusion matrix. Runs in milliseconds with no external model. The same set also feeds a stratified 5-fold stability check: folds are dealt round-robin by SIF label x language, and the UI reports mean ± std with a 95% confidence interval — so the metrics are checked for stability across case compositions, not a single lucky split.

A second, statistical benchmark runs from the same Evaluation page: stratified 5-fold cross-validation over a 500-report dataset (Multinomial Naive Bayes / Logistic Regression / Linear SVM vs the rule-engine baseline, F2-weighted, TF-IDF fit inside each fold). Results served by /api/model/evaluate.

Feedback-to-retraining loop

Each HSE review (verify / reject / edit) becomes a labeled example. The "Train on reviewed labels" pass recomputes model-to-human agreement, mines the surface phrases behind disagreements, and applies them as weighted learned signals to later analyses — tagged rules-v1+tuned and flagged for review. A learned keyword alone never flips a verdict; rules and human review stay in control.

Roadmap for real data: train-on-synthetic-test-on-real (TSTR), distribution fidelity checks (KS / chi-square), and a real-vs-synthetic discriminator once an HSE-labeled real dataset exists.
